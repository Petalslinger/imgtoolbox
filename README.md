# 图片工具箱

一个跑在浏览器里的图片批量处理工具，四个**互相独立**的功能分区：

| 分区 | 做什么 | 输出 |
|---|---|---|
| **批量重命名** | 只改文件名，图片内容一个字节不动 | ZIP |
| **改分辨率** | 只改尺寸，格式和文件名不动 | ZIP |
| **转格式** | 只换图片编码，尺寸和文件名不动 | ZIP |
| **导出 PDF** | 把勾选的图合并成一份 PDF | 单个 PDF |

零安装、零后端、零上传——图片一个字节都不离开你的电脑。双击 `index.html` 就能用。

> 从工作区里那个 Python 版 `png2pdf` 继承来的：数字感知排序、透明区垫白底、
> 1px = 1pt 的 PDF 页面尺寸、以及 PDF 一页一张图的行为。

## 快速开始

1. 双击 `index.html`（Chrome / Edge / Firefox / Safari 都行）
2. 点「添加图片…」或「添加文件夹…」，图片进入左栏**文件池**
3. 在左栏勾选要处理的图，必要时拖 ≡ 调整顺序
4. 点上方四个标签之一，设好那个分区的参数，点底部的执行按钮

四个分区用的是**同一批图**（文件池），但**设置互不影响**。比如你在「改分辨率」
里设了 1920px，切到「导出 PDF」导出的仍然是原图，不会被缩放。

想确认工具在你的浏览器里一切正常，双击 `selftest.html`，它会真跑一遍核心逻辑并逐项列出结果。

---

## 文件池（左栏）

- 四个分区共用这一批图。这解决的是「处理哪些图」，**不是流水线**
- **顺序就是导出顺序**：决定 PDF 的页序，也决定重命名时的编号顺序
- 排序：数字感知（`1,2,…,10` 而不是 `1,10,2`）/ 字典序，可升可降
- 手动排序：拖 ≡ 手柄，或用方向键；拖过之后不会被自动排序覆盖，可点「还原排序」
- 勾选：框选参与本次处理的那几张；全选 / 全不选 / 反选
- 被重命名或被换后缀的图，名字下面会多显示一行 `→ 导出后的名字`

## 分区一：批量重命名

规则按从上到下叠加，每条都能单独关掉：

| 规则 | 参数 |
|---|---|
| ① 查找替换 | 查找 / 替换为，可选**按正则表达式**、可选区分大小写 |
| ② 加前缀 / 后缀 | 固定串 |
| ③ 重新编号 | 起始值、步长、补零位数（1–12）、分隔符、编号位置（前/后）、升序/降序 |

下方实时显示「原名 → 新名」逐条对照。**有重名会标红并阻止执行**——因为 ZIP 里同名条目会互相顶掉。

正则写错时会跳过那一步而不是崩掉。

---

## 分区二：改分辨率

- 三种模式：**按宽度 / 按高度 / 按百分比**
- **只允许填一个方向，另一边永远等比算出来**——所以输出的宽高比必然等于原图，
  不存在拉伸变形这种可能
- 默认**禁止放大**：800px 的图设成 1920px 只会变糊，不如保持原样。要放大得手动勾选
- 重采样用 `imageSmoothingQuality: 'high'`
- 预设：1920 / 1280 / 1080 / 800 / 640 / 50% / 25%
- 底部会告诉你：有几张会真的改变尺寸、几张保持不变、几张因为「禁止放大」而没按目标放大

---

## 分区三：转格式

- PNG / JPEG / WebP 互转
- JPEG 和 WebP 带质量滑块（PNG 是无损的，没有这个参数）
- **转成 JPEG 时透明区域自动垫白底**，不会变黑（对齐原 png2pdf 的 `to_rgb()`）
- 可勾选「自动把后缀换成新格式」；关掉的话文件名后缀不变，但内容是转换后的格式
- 个别浏览器不支持 canvas 编 WebP，会自动降级成 PNG，**文件名跟着真实格式走**，
  不会出现「叫 .webp 实际是 PNG」

---

## 分区四：导出 PDF

- 一图一页，**页面尺寸 = 图片像素尺寸**（1px = 1pt），和原 `png2pdf` 一致
- 页序 = 左栏顺序
- 导出的**永远是原图**，不受另外两个分区影响
- 下方列出将写入的页序和每页尺寸，并粗估体积

### 为什么这里把图片统一重编码成 JPEG

原来的做法是「能无损内嵌就无损内嵌」：JPEG 直接搬字节，8 位 PNG 把 IDAT 片段
原样搬进 `/FlateDecode` 流。听起来更优，但那条路踩了一连串坑——要自己扫 PNG 的
chunk、判断色彩类型、确认它是内联的 deflate 流。任何一处判断错，产出的就是一个
**能下载但打不开的 PDF**：最坏的失败模式，用户完全看不出原因。

改成统一「解码 → 垫白底 → 编码成基线 JPEG → `/DCTDecode` 内嵌」之后：

- JPEG 是完整自包含的字节流，PDF 阅读器直接交给 JPEG 解码器，兼容性最好
- 代码路径短得多，没有需要我猜的地方
- 代价：JPEG 有损。已经在用 JPEG 的图质量设 0.95，损失很小；
  无损的 PNG 会有轻微损失

**另外，写出器会自己验收。** `PdfWriter.build()` 拼完一版字节之后会：

1. 逐字段解析交叉引用表，核对每个对象的偏移是否精确落在 `N 0 obj` 上
2. 检查 `startxref`、`/Size`、`%%EOF`、以及 `/Length undefined` 这类非法字面量
3. 把每个图片流**真的解压出来**，检查字节数是否等于 `高度 × (1 + 宽度 × 通道数)`

任何一页验不过，就把它换成 JPEG 重写一版再验。**验不过就报错，绝不把坏文件交出去**——
「能下载但打不开」是比「明确报错」糟糕得多的结果。

## 输出

处理结果通过浏览器下载给你，**原图一个字节都不会被修改**。所以不需要任何目录授权，
也不存在「把原图改坏了」的风险。

- ZIP：用浏览器原生 `CompressionStream` 压缩，文件名按 UTF-8 写入并置通用标志位
  bit 11，中文名不会乱码。压缩不可用时自动退回不压缩
- 用「添加文件夹」加进来的图，ZIP 里会保留相对目录结构
- 输出名自动生成（如 `图片_改分辨率_20250131.zip`），也可以用 PDF 分区里的输入框自定义

## 文件结构

```
imgtoolbox/
├── index.html          工具箱本体，双击打开
├── selftest.html       自检页（开发用），加载真实模块跑 11 组断言
├── README.md
├── PUBLISH.md          上传到 GitHub 的步骤
├── LICENSE             MIT
├── .gitignore
├── css/
│   └── style.css
└── js/
    ├── util.js           通用工具：数字感知排序、字节处理、DOM、Toast
    ├── pdfwriter.js      自研 PDF 写出器 + 自我验证（xref 解析、流校验）
    ├── zipwriter.js      自研 ZIP 写出器（CRC-32 + deflate/store）
    ├── state.js          全局状态（文件池、排序、勾选）
    ├── rename.js         重命名规则引擎 + 重名检测
    ├── transform.js      缩放数学 + 像素处理（唯一实现，主线程与 Worker 共用）
    ├── worker-source.js  Worker 的消息循环源码（字符串形式）
    ├── workerhost.js     Worker 宿主：起线程、注入实现、派活、进度、取消
    ├── pdf.js            PDF 装配（解码 → 垫白底 → 基线 JPEG）
    ├── pool.js           文件池：收文件、量尺寸、排序、勾选、拖拽
    ├── sections.js       四个分区的界面与参数
    ├── exporter.js       四个分区各自的执行入口
    └── app.js            界面装配、分区切换、进度与结果提示
    （steps.js 和 preview.js 是旧流水线设计的遗留空壳，可以删）
```

**没有第三方库，没有构建步骤，没有 `node_modules`。** PDF 和 ZIP 的编码器都是手写的，
所以这个文件夹拷到任何一台电脑、双击就能跑，离线也能跑。

### 为什么用传统 `<script>` 而不是 ES module

`file://` 协议下 ES module 会被 CORS 直接拦死，双击打不开页面。传统 `<script>` 标签没这个问题。

同理，Worker 不是从独立文件加载，而是从字符串起一个 Blob URL（`file://` 下加载独立
`worker.js` 同样会被拦）。像素处理的实现只有一份（`transform.js`），主线程把这些函数的
**源码字符串**发给 Worker，由 Worker 自己 `eval` 出来，这样两边跑的是同一份代码。
主线程侧还有一道静态自检：如果这些函数引用了没被一起注入的辅助函数，会明确报错并退回
主线程处理，而不是让 Worker 里悄悄算错。

## 浏览器要求

| 能力 | 缺失时的降级 |
|---|---|
| File API、canvas | 硬性要求 |
| `CompressionStream('deflate-raw')` | ZIP 退回不压缩 |
| `DecompressionStream` | **无法导出 PDF**（写出器的自检要用它解压验证），会明确报错 |
| `createImageBitmap` | 退回 `<img>` + objectURL 解码 |
| `OffscreenCanvas` | 退回 `document.createElement('canvas')` |
| Worker | 退回主线程串行处理，界面会卡但结果正确 |
| canvas 编 WebP | 自动降级成 PNG |

实测正常：Chrome / Edge 近几年的版本。Firefox 与 Safari 对 `file://` 下 Blob Worker 较严格，
可能会走主线程兜底，功能不受影响。

## 已知取舍

- **导出 PDF 会重新编码成 JPEG**，不再保留 PNG 无损。上面「为什么这里把图片统一重编码成
  JPEG」一节解释了原因：为了可靠。如果你更看重无损、且愿意接受偶尔打不开的风险，
  可以在 `js/pdf.js` 里改回「能无损内嵌就无损内嵌」。
- **不支持裁剪**。缩放决定「交付出去多大」，裁剪决定「画面里有什么」，两者是搭档不是替代；
  当前版本只做缩放，守住「不变形」的方式是「只允许填一个方向」。
- **GIF 只取首帧**，不做动图。
- **AVIF 能读、能打包进 ZIP、也能进 PDF**（会重编码），但转格式分区里不提供 AVIF 输出。
- **超过 100 张会提示分批**，是软警告不拦你。浏览器内存吃紧时可能变慢甚至失败。
- **一次只跑一个分区**。想「先缩到 1080 再转成 JPEG」就分两步做：先跑改分辨率分区导出
  ZIP，再把那个 ZIP 解出来跑转格式分区。
