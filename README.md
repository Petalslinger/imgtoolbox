# 图片工具箱

一个在浏览器中运行的图片批量处理工具，包含四个**互相独立**的功能分区：

| 分区 | 功能 | 输出 |
|---|---|---|
| **批量重命名** | 仅修改文件名，图片内容不做改动 | ZIP |
| **改分辨率** | 仅修改尺寸，格式与文件名不变 | ZIP |
| **转格式** | 仅更换图片编码，尺寸与文件名不变 | ZIP |
| **导出 PDF** | 将选中的图片合并为一份 PDF | 单个 PDF |

无需安装、无后端、无上传：图片不离开本机。双击 `index.html` 即可使用。

> 沿用工作区中 Python 版 `png2pdf` 的行为：数字感知排序、透明区填充白底、
> 1px = 1pt 的 PDF 页面尺寸，以及 PDF 一页一张图。

git clone https://github.com/Petalslinger/imgtoolbox.git

没有依赖需要安装，也没有构建步骤——克隆后双击 `index.html` 即可使用。

## 快速开始

1. 双击 `index.html`（支持 Chrome / Edge / Firefox / Safari）
2. 点击「添加图片…」或「添加文件夹…」，图片进入左栏**文件池**
3. 在左栏勾选待处理的图片，必要时拖动 ≡ 调整顺序
4. 切换上方标签选择分区，设置该分区参数后点击底部执行按钮

四个分区共用**同一文件池**，但**参数相互独立**。例如在「改分辨率」
里设置 1920px 后切换至「导出 PDF」，导出的仍为原图，不受缩放影响。

如需验证工具在当前浏览器中的运行情况，双击 `selftest.html`，它将实际执行核心逻辑并逐项列出结果。

## 文件池（左栏）

- 四个分区共用这批图片。该区域决定「处理哪些图片」，**并非处理流水线**
- **顺序即导出顺序**：决定 PDF 的页序，也决定重命名时的编号顺序
- 排序：数字感知（`1,2,…,10` 而非 `1,10,2`）/ 字典序，可升可降
- 手动排序：拖动 ≡ 手柄或使用方向键；手动调整后不再被自动排序覆盖，可点击「还原排序」
- 勾选：选中参与本次处理的图片；全选 / 全不选 / 反选
- 重命名或更换后缀的图片，会在文件名下方额外显示一行 `→ 导出后的名字`

## 分区一：批量重命名

规则按从上到下依次叠加，每条均可单独启用或关闭：

| 规则 | 参数 |
|---|---|
| ① 查找替换 | 查找 / 替换为，可选**按正则表达式**、可选区分大小写 |
| ② 加前缀 | 固定串 |
| ③ 重新编号 | 起始值、步长、补零位数（1–12）、分隔符、编号位置（前/后）、升序/降序 |

下方实时显示「原名 → 新名」逐条对照。**检测到重名时标红并阻止执行**：ZIP 中同名条目会相互覆盖。

正则表达式非法时跳过该步骤，不会中断执行。

---

## 分区二：改分辨率

- 三种模式：**按宽度 / 按高度 / 按百分比**
- **仅允许填写一个方向，另一方向按等比自动计算**，因此输出的宽高比必然等于原图，
  不会发生拉伸变形
- 默认**禁止放大**：将 800px 的图片放大到 1920px 只会降低清晰度，故保持原尺寸。如需放大须手动勾选
- 重采样使用 `imageSmoothingQuality: 'high'`
- 预设：1920 / 1280 / 1080 / 800 / 640 / 50% / 25%
- 底部显示：实际改变尺寸的图片数、保持不变的图片数，以及因「禁止放大」而未按目标缩放的图片数

---

## 分区三：转格式

- PNG / JPEG / WebP 互转
- JPEG 与 WebP 提供质量参数（PNG 为无损格式，无此参数）
- **转换为 JPEG 时透明区域自动填充白底**，不会变黑（对齐原 png2pdf 的 `to_rgb()`）。
  注意缩放同样会填充白底：图片一旦被重新绘制（尺寸改变），透明区域即变为白色。
  如需保留透明度，则不要缩放或转格式——该情况下原文件按字节原样透传
- 可勾选「自动把后缀换成新格式」；取消勾选时文件名后缀不变，内容仍为转换后的格式
- 部分浏览器不支持通过 canvas 编码 WebP，此时自动降级为 PNG，**文件名与真实格式一致**，
  不会出现后缀为 .webp 而内容为 PNG 的情况

## 分区四：导出 PDF

- 一图一页，页面尺寸默认取图片像素尺寸（1px = 1pt），与原 `png2pdf` 一致
- **统一页面宽度**（默认启用）：以最宽一张的宽度为准，其余图片等比缩放到该宽度，
  因此各页等宽。窄图被放大、宽图保持不变，**宽高比不变**，不会变形。
  如需每页使用各自的原图尺寸，取消勾选
- 页序 = 左栏顺序
- 导出的**始终是原图**，不受另外两个分区影响
- 输出文件名可自定义；留空则自动命名，并可选择**是否附加时间戳**（默认附加）——
  取消勾选后文件名固定不变，适用于反复生成并直接覆盖的场景
- 下方列出将写入的页序与每页尺寸，并估算体积

### 为什么统一将图片重编码为 JPEG

原方案为「可无损内嵌则无损内嵌」：JPEG 直接搬运字节，8 位 PNG 将 IDAT 片段
原样写入 `/FlateDecode` 流。该方案理论上更优，但需自行扫描 PNG 的 chunk、
判断色彩类型、确认其为内联的 deflate 流；任一环节判断错误，产出的即为
**能下载但无法打开的 PDF**，且用户无法判断原因，属最严重的失败模式。

改为统一「解码 → 填充白底 → 编码为基线 JPEG → `/DCTDecode` 内嵌」后：

- JPEG 为完整自包含的字节流，PDF 阅读器可直接交由 JPEG 解码器处理，兼容性最佳
- 代码路径显著缩短，无需依赖推测
- 代价：JPEG 为有损格式。原为 JPEG 的图片质量设为 0.95，损失很小；
  无损的 PNG 会有轻微损失

**另外，写出器会在生成后自行校验。** `PdfWriter.build()` 组装完字节后执行：

1. 逐字段解析交叉引用表，核对每个对象的偏移是否精确落在 `N 0 obj` 上
2. 检查每个流在 `/Length` 声明的位置之后是否紧跟 `endstream`，
   以及 `startxref`、`/Size`、`%%EOF`、`/Length undefined` 这类非法字面量
3. 核对每张内嵌图：JPEG 必须以 `FFD8` 开头、`FFD9` 结尾，缺一即判为被截断

**校验不通过即报错，不会输出损坏文件**——相比「明确报错」，「能下载但打不开」
的后果严重得多。此处为**拒绝交付**，不进行自动重写；任一页存在问题，整份 PDF 均不生成。

## 输出

处理结果通过浏览器下载，**原图不会被修改**，因此不需要任何目录授权，
也不存在损坏原图的风险。

- ZIP：使用浏览器原生 `CompressionStream` 压缩，文件名以 UTF-8 写入并置通用标志位
  bit 11，中文名不会乱码。压缩不可用时自动退化为不压缩
- 通过「添加文件夹」导入的图片，在 ZIP 中保留相对目录结构
- 输出文件名自动生成（如 `图片_改分辨率_20250131.zip`），也可通过 PDF 分区的输入框自定义

## 文件结构

```
imgtoolbox/
├── index.html          工具箱主页面，双击打开
├── selftest.html       自检页（开发用），加载真实模块执行断言
├── README.md
├── PUBLISH.md          上传到 GitHub 的步骤
├── LICENSE             MIT
├── .gitignore
├── css/
│   └── style.css
└── js/
    ├── util.js           通用工具：数字感知排序、字节处理、DOM、Toast
    ├── pdfwriter.js      自研 PDF 写出器 + 自我验证（xref 解析、流校验）
    ├── zipwriter.js      自研 ZIP 写出器（CRC-32 + deflate/store）
    ├── state.js          全局状态（文件池、排序、勾选）
    ├── rename.js         重命名规则引擎 + 重名检测
    ├── transform.js      缩放数学 + 像素处理（唯一实现，主线程与 Worker 共用）
    ├── worker-source.js  Worker 的消息循环源码（字符串形式）
    ├── workerhost.js     Worker 宿主：创建线程、注入实现、任务分发、进度、取消
    ├── pdf.js            PDF 装配（解码 → 填充白底 → 基线 JPEG）
    ├── pool.js           文件池：接收文件、读取尺寸、排序、勾选、拖拽
    ├── sections.js       四个分区的界面与参数
    ├── exporter.js       四个分区各自的执行入口
    └── app.js            界面装配、分区切换、进度与结果提示
```

**无第三方库、无构建步骤、无 `node_modules`。** PDF 与 ZIP 编码器均为手写实现，
因此该目录可复制到任意一台电脑直接双击运行，也可离线运行。

### 为什么使用传统 `<script>` 而非 ES module

在 `file://` 协议下，ES module 会被 CORS 策略直接阻止，导致页面无法通过双击打开；
传统 `<script>` 标签不存在这一问题。

同理，Worker 不从独立文件加载，而是由字符串创建 Blob URL（`file://` 下加载独立
`worker.js` 同样会被阻止）。像素处理的实现仅有一份（`transform.js`）：主线程将这些函数的
**源码字符串**发送给 Worker，由 Worker 自行 `eval`，从而保证两侧运行同一份代码。
主线程侧另有一道静态检查：若这些函数引用了未被一并注入的辅助函数，将明确报错并回退到
主线程处理，避免 Worker 内出现静默计算错误。

## 浏览器要求

| 能力 | 缺失时的降级 |
|---|---|
| File API、canvas | 硬性要求 |
| `CompressionStream('deflate-raw')` | ZIP 退化为不压缩 |
| `DecompressionStream` | **无法导出 PDF**（写出器自检需用它进行解压验证），会明确报错 |
| `createImageBitmap` | 回退为 `<img>` + objectURL 解码 |
| `OffscreenCanvas` | 回退为 `document.createElement('canvas')` |
| Worker | 回退为主线程串行处理，界面会卡顿但结果正确（控制台会给出说明） |
| canvas 编码 WebP | 自动降级为 PNG |

实测正常：近年版本的 Chrome / Edge。Firefox 与 Safari 对 `file://` 下的 Blob Worker 限制较严格，
可能回退到主线程，功能不受影响。

## 已知取舍

- **导出 PDF 会重新编码为 JPEG**，不再保留 PNG 无损。原因见上文
  「为什么统一将图片重编码为 JPEG」一节：为保证可靠性。
- **任一页存在问题，整份 PDF 均不生成**。写出器自检采用「全部通过才交付」策略，
  不会跳过异常页，因此不会产生缺页的 PDF。
- **不支持裁剪**。缩放决定输出尺寸，裁剪决定画面内容，两者互补而非替代；
  当前版本仅实现缩放，通过「只允许填写一个方向」保证不变形。
- **GIF 仅取首帧**，不支持动图。
- **AVIF 可读取、可打包进 ZIP、也可写入 PDF**（会重编码），但转格式分区不提供 AVIF 输出。
- **超过 100 张时会提示分批处理**，该提示为软性警告，不会阻止执行；浏览器内存紧张时可能变慢甚至失败。
- **一次仅执行一个分区**。如需「先缩放到 1080 再转换为 JPEG」，可分两步：先运行改分辨率分区导出
  ZIP，解压后再运行转格式分区。
